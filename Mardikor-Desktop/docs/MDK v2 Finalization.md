## 3. 2026-11-17：MDK 禁止压缩，MDKE 承担压缩分发

根据明确的格式设计决定，v2 的 ZIP 普通文件和目录一律使用 STORE（方法 0）。原定稿中允许 DEFLATE（方法 8）的条款被替代，所有非 0 方法均不合法，包括压缩等级 0、空条目或没有实际缩小体积的情形。正文、TOML、资源、状态、扩展及未知附件没有例外。

这是收紧格式合法性的显式修订，不是文字勘误；本次沿用 `format_version = 2`，设置能力版本和正文模型不变。旧修订生成的 DEFLATE 文件不再符合当前要求，但不因此断言其数据损坏。读取器报告容器 `fail`／`mdk.container.invalid`／`error`，不得把自动解压作为正常打开的兼容步骤。可选转换工具必须经用户显式操作、验证数据并输出到新文件，保留源文件。

全 STORE 仅限制 MDK 封装，不要求把 JPEG／PNG 等媒体转换成无压缩编码。需要压缩分发时生成 `.mdke`。本节修订完成时，访问保护及 MDKE 尚处规划阶段；后续独立规范及定稿状态见第 5 节。

本次容器规则的文档修订只修改规范和说明，不修改客户端、构建或检查脚本。该修订完成时，桌面端及示例脚本仍有 DEFLATE 写入路径；这是当时的实现记录，不表示后续工程适配的状态。先前的实现采用声明和第 2 节验证记录仅对应旧修订，不能证明已满足全 STORE 要求。

主规范同步更新容器配置、失败诊断、操作矩阵、保存流程、无损保留和安全表述，并增加 STORE／DEFLATE、媒体编码及改名伪装的四项检查用例。当前一致性用例共 57 条；新增条目是后续实现需要覆盖的要求，不表示本轮已执行应用测试。

本次文档检查通过：4 份修改或新增文档的 25 个本地链接均可解析，16 个规范片段与磁盘示例一致，其中 10 个 TOML 片段通过语法解析；§17 的用例数量核对为 57。没有运行应用测试或示例归档生成脚本。

## 4. 2026-11-17：跨平台访问保护与 MDKE 设计稿

本节记录 Draft 1 阶段，已由第 5 节定稿接续，旧方案入口现在指向现行规范。当时将早期规划整理为一套候选设计：MDKP 对全 STORE 工程认证加密，MDKE 以 Zstandard 或 STORE 原样封装单个 MDK，两层口令独立，解包逐字节还原输入。受保护 MDK 默认不再次压缩，明确保留访问保护与压缩收益之间的取舍。

候选布局明确魔数、32／144 字节头、1 MiB 数据分块、结束记录、认证范围及错误处理。密码学配置采用 Argon2id 的 64 MiB／3 次／1 lane 可移植配置，以及 XChaCha20-Poly1305 密钥包装和 secretstream；口令统一按 Unicode 15.1 NFC 编码。该单 lane 选择替代早期四 lane 候选，不宣称是 RFC 9106 四 lane 推荐配置的原样实现。

方案面向 Windows、macOS、Linux、Android、iOS 和 WebAssembly，另规定 64 位长度、资源限额、加密恢复和不支持原子覆盖时的另存策略。该轮仅修改方案及规范引用；裸 v2 ZIP 的规则不变。Draft 1 当时尚未定稿，测试向量、跨平台互操作、设备基准和独立安全评审也未执行；后续定稿不追溯声称这些验收已经通过。

本轮静态检查通过：3 份文档的 20 个本地链接、三个二进制布局表的偏移和总长度、三个魔数及块／结束记录长度计算；主规范的 16 个示例片段仍与磁盘文件一致，其中 10 个 TOML 片段通过语法解析。这些检查只验证文档结构和数值一致性，不是密码学或应用互操作测试。

## 6. 2026-11-20 · 通用附件导入、引用与预览

[主规范](<MDK Format Specification v2.md>) §9.4–9.6 规定工程写入器接收任意普通文件，基础预览器提供文件信息及原样提取。作者使用标准 Markdown 链接访问附件，使用图片语法请求正文插图。音视频、PDF、文本等可在读者激活后使用受限预览。§11.4 和 §14.1 分别规定出版目标不可表达附件链接、仅用于提取的附件可完整交付时的处理。

本次为 v2 核心行为扩展，沿用既有的全 STORE ZIP、相对 URL 和正文语法。新增[附件示例工程](examples/v2/attachments/)和八条一致性用例，涵盖无扩展名、空文件、引用改名、预览降级及交付与出版的区别。本次交付范围为格式文档和示例；各客户端的支持情况以其版本文档为准。

已用现有 CLI 打包、校验并解包附件示例，7 个文件逐字节一致，所有条目均为 STORE 且 CRC 校验通过。Markdown 解析检查确认 1 处图片和 3 处普通链接均指向预期文件。原示例检查通过，§17 现有 65 条一致性用例。预览界面行为留待客户端按新增用例验收。

## 7. 2026-11-20 · 大文件容量与视频资源

[主规范](<MDK Format Specification v2.md>) §3.5 将容量分为单项数据、快照数据总量、含 ZIP 开销的容器长度，以及操作期间各卷需要的空间。普通 MDK 沿用全 STORE 和单卷 ZIP64，`format_version = 2`。视频可直接使用 §9.5 的普通链接；保存、提取及交付保留其完整原始字节。播放、正文编辑、出版、加密和分发按各自的资源预算判断。

修订前的桌面端和 CLI 构建使用 64 MiB／256 MiB 固定容量。0.3.4 的适配构建贯通文件选择、拖入、CLI 导入、容器读写、修订摘要、资源提取和交付。大条目保留为验证后的磁盘区间，普通 MDK 的原子写出按目标空间和写入配额检查。MDKP／MDKE、文本命令和出版资源仍使用各自的操作预算。实现入口见[归档校验](../electron/archive.ts)、[工程读写](../electron/mdk.ts)、[拖入资源](../electron/insertion-assets.ts)和[封装处理](../electron/envelope.ts)。

§17 新增七组容量用例。桌面及 CLI 验收须用真实流式输入覆盖旧上限、900 MiB 视频和跨 4 GiB 的长度／偏移，记录源文件与提取文件的摘要、峰值内存、所需临时空间和取消后的磁盘状态。受保护工程及 MDKE 须分别验证封装和还原流程。本文只记录格式修订及后续实现的验收条件。

文档示例检查通过，§17 现有 72 条用例。另用内存中的稀疏 STORE 容器核对了单项 64 MiB、数据总量 256 MiB、物理包长 256 MiB 各自的前一字节、边界值和后一字节。独立 ZIP 读写验证覆盖一个 4 GiB + 1 字节条目及四个 1 GiB 条目，均能读取位于 4 GiB 之后的末项并完成数据 CRC 检查。这是容器边界验证；实际客户端的大视频导入、播放及保存仍待开发验收。
